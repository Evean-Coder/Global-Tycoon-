# 游戏可用性整改 Plan

> 当前状态：2026-10-09已完成本轮限定验收，见[acceptance.md](acceptance.md)。下文保留审批时的目标、设计和阶段记录。

日期：2026-10-08。版本：1.0。依据：[已批准的spec.md](spec.md)。状态：已批准，进入任务拆解。

本设计仅实现手机地图与方向提示、股票窗口及反馈整改、机场费用说明和规则速查。周期性可跳过经营机遇保留为后续独立玩法项目。现有规则数值、动作含义和联机流程按spec.md保持兼容。

## 现有实现与风险依据

- 手机样式隐藏地块名称、归属和房屋/抵押标记，是已复现的显示问题。
- 股票窗口由服务端生成并记录累计买入；连续两个正常窗口购买已经通过受控核查。本轮不能把问题归因为服务端统一不重置额度。
- 前端股票阶段结束仅收起弹窗，未同步清理草稿；成交或失败回调直接修改全局草稿并可能继续发送结束窗口动作，没有检查原请求是否仍属于当前窗口。这里是需要验证和防护的风险，不等于已复现玩家报告。
- 服务端已有本人飞行报价及远航开支阶段；当前飞行等待状态没有明确记录本次已付机场通行费。展示实际已付金额需要补充只读结算信息，不能用当前机场数量反推历史扣款。

## 架构概览

### A1：棋盘布局与旋转提示

保留现有42格原生按钮、世界地图、资产卡和地块详情入口。修正窄屏样式，使名称、归属及房屋/抵押标记常显；为手机横屏建立适合短屏的布局，优先增加地块宽度，允许纵向滚动。大厅和房间增加非阻塞横屏提示，对局竖屏继续提醒。

布局变化继续通过现有棋子定位及操作栏留白流程适配。旋转只调整显示，不重新初始化对局、草稿、当前决定或计时器。手机与平板以视口条件适配，避免横屏手机仅因宽度超过原窄屏断点而落入不合适布局。

覆盖：F1、F2；AC1–AC4。

### A2：股票窗口上下文与回执处理

在现有股票渲染、数量调整、提交及转让流程上增加明确的窗口上下文。草稿、错误、报价依据和自动弹出状态属于具体对局、本人和股票窗口。状态接收时识别窗口关闭或切换，即时使旧上下文失效；同一窗口返回或重连沿用服务端累计额度。

股票提交、放弃和成交后自动结束窗口的回调都检查原上下文；旧结果不得修改新草稿、关闭新弹窗或发送新窗口动作。请求重试沿用原动作身份，保留现有服务端幂等及交易原子性。真实状态接收与视觉动画完成分开处理上下文有效性，避免动画排队期间使用旧窗口执行操作；保持原动画顺序。

覆盖：F3、F5；AC5–AC7、AC10、AC11。

### A3：股票限制、报价和错误展示

从本人视图、现有股票状态及当前草稿计算只读交易预览，集中给出单城/总股数/城市数的剩余额度、全城供给、本人城市持股上限和批次净现金。数量调整、按钮状态、错误说明及提交前检查复用同一组前端计算，最终合法性仍由服务端裁定。

报价变化时保留同窗口数量，明确标记原报价失效、显示最新金额，并要求再次确认。区分交易失败、连接未确认和实际成交；不能自动接受新价格或把他人城市也限制为持有4股。卖出其他城市的收入计入同批可用现金。

覆盖：F4、F5；AC8–AC11。

### A4：飞行费用资料与现有结算

机场落地结算时保存本次通行费的只读事实，并在现有本人视图中提供飞行费用摘要；不增加收费或改变免费条件。前端复用服务端飞行报价、优惠效果和远航开支阶段，分别展示出发/目的机场归属、已付通行费、待确认机票和回合结束开支。

对缺少新增资料的旧状态采取明确兼容展示：无法确认历史已付金额时说明该项未提供，不能编造金额；既有免费标志和当前真实报价仍有效。新费用版本与旧局根据服务端状态区分，保留既有自救和回合推进。

覆盖：F6；AC12、AC13。

### A5：规则资料、主题导航与交付验证

保留规则弹窗入口，按主题导航及可展开内容组织真实规则和常见疑问。十二项机遇复用现有规则目录与效果资料，补充触发、上限及排除条件；费用说明根据大厅发布配置或当前对局版本生成。玩家玩法文档与页面资料在同一批修改中核对。

同步更新页面资源版本和离线缓存。沿用现有受控引擎、Socket及浏览器测试工具补充本轮场景；验证地图布局、窗口故障、费用和规则资料，不运行完整胜率模拟。静态说明与动态玩家名称安全显示，维持本人视图隐私边界。

覆盖：F7、F8、N1–N6；AC14–AC19，并支持前述模块回归。

## 核心数据与接口

### D1：股票窗口上下文

当前正式玩法及未启用远航费用的旧v2对局，均沿用`self.stockWindow`中的`windowId`、`playerId`、`boughtByCity`、`boughtTotal`和报价数据，不新增Socket事件或客户端额度重置动作。

| 本地字段 | 含义及约束 |
|---|---|
| `key` | 由`gameId`、本人`playerId`、服务端`windowId`组成；不使用会因转让确认而变化的`decisionId`充当窗口身份。 |
| `generation` | 本地上下文代次；关闭或更换窗口时递增，使旧回调失效。 |
| `draft` | 按城市保存`buy`、`sell`及`basis`；`basis`包含玩家看到的`price`、`quoteVersion`、`listingEpoch`。不从旧窗口复制。 |
| `transferDraft` | 同窗口的转让草稿；转让界面返回不重置累计额度，新窗口或新对局清理。 |
| `status`、`error` | 区分可编辑、等待回执、需更新报价、未确认及等待状态同步；错误只属于匹配窗口。 |
| `autoShown` | 本窗口是否自动打开；转让确认期间保留上下文，返回股票阶段后允许按原流程恢复界面。 |
| `pendingRequest` | 本次请求的身份、上下文代次、原订单和期望状态版本；仅用于回执匹配与恢复，不作为已成交证据。 |

`syncStockContext(state)`在接收真实状态时调用：窗口身份相同则保留草稿；窗口不存在、本人身份改变或新对局则失效并清理。`trade_confirm`期间只要服务端仍保留同一`self.stockWindow`，就不误判成新窗口或重置额度。视觉动画尚未完成时，不开放基于旧渲染状态的股票操作。

历史v1状态没有现代窗口及报价协议：保留原规则分支，采用房间/开局时间、当前玩家和本地窗口代次隔离草稿；不伪造现代累计额度或为旧局迁移规则。此分支的股票请求不自动重发缺少幂等身份的订单，未确认时先核对真实状态；旧局费用始终按其原版本展示。

### D2：统一股票预览

`stockPreview(state, playerId, draft)`为只读计算，返回全局汇总及各城市条目；`renderStock`、`adjStock`和`submitStock`复用它，服务端`planStockTrade`仍是最终裁定者。

| 输出 | 数据来源与计算约定 |
|---|---|
| `windowUsage`、`remaining` | 服务端已买总股数/城市集合/各城数量，另列草稿占用；城市数按已买与草稿买入城市的并集计算。卖出不返还本窗口累计买入额度。 |
| `cityRows` | 实际归属、清算资格、本人持股、全城已发股数、剩余供给、窗口单城剩余及本人城主4股限制。v2抵押城市仍可交易；无主或清算城市按现有规则不可交易。 |
| `cost`、`proceeds`、`netCash` | 使用当前真实报价计算可见预览，另保留旧`basis`供提示差异；可用现金为本人现金加其他城市的同批卖出收入。 |
| `reasons`、`canIncrementBuy`、`canIncrementSell` | 汇总阶段/身份、额度、供给、持股、现金及未确认状态，生成就地原因与按钮状态。减少数量始终可用于修正有效草稿。 |
| `quoteChanged`、`invalidOrders` | 比较价格、报价版本、上市批次与草稿依据；标出持股、清算或额度改变造成的订单失效。 |

数量按安全整数处理；每座城市v2草稿只能买或卖一种方向，卖出量不得超过实际持股。不能把供给上限20股或城主4股上限误用为其他玩家的个人4股上限。

报价变化时保留数量并展示旧/新依据。`refreshStockDraftQuotes(context)`只更新可见依据并重新预览，不发送动作；界面先提供“更新报价”，更新后再由“确认交易”明确提交。不会在失败回调里静默改版本再自动成交。

### D3：请求与回执约定

保留`action`事件和原订单格式：现代股票交易仍发送`windowId`及每项订单的`cityId`、`side`、`shares`、`quoteVersion`、`listingEpoch`，外层沿用`gameId`、`actionId`、`decisionId`和`actorRevision`。不添加新的游戏动作。

| 接口 | 责任 |
|---|---|
| `captureStockContext()` | 捕获请求所属窗口、代次及订单依据。提交前要求最新服务端状态与当前可操作界面一致。 |
| `isCurrentStockContext(context)` | 比较最新接收状态和本地代次；用于交易、放弃、转让发起及相关回执的所有后续界面修改。 |
| `sendAction(action, callback, options)` | 兼容已有调用；股票操作提供上下文守卫及请求令牌。只由当前请求令牌释放操作锁；过期请求不重发、不显示到新窗口、不执行其回调副作用。 |
| `submitStock()` | 预览校验后捕获窗口与报价发送；失败仅更新匹配窗口。成功先核对服务端状态版本，再清理相应草稿并按原流程结束同一窗口。 |
| `finishStockAfterReceipt(context, receipt)` | 仅在收到匹配窗口成功回执、真实状态版本至少达到回执版本、当前仍为本人股票阶段且动画已完成时发送`stock_done`；若状态尚未呈现，等待现有状态/渲染流程；窗口已关闭则不再发。 |

自动超时重试仅在原上下文仍有效且协议具备幂等身份时，重发完全相同的载荷与`actionId`。无确认结果显示“未确认”，不能产生新动作身份自动补单。服务端保持现有成功请求缓存、复制状态校验后统一提交与拒绝动作不延时行为。

### D4：机场费用事实与本人视图

新增的`airportFeePaid`仅记录现有结算已经发生的事实，放在本次飞行的等待状态内：`playerId`、`airportId`、`ownerId`、`amount`。自家机场为已确认的0；他人机场记录原结算计算出的实际金额。记录不调用新的结算、不计入机场收费公式，也不改变原现金不足自救路径。

本人视图新增只读`self.flightInfo`，仅当本人正处于飞行阶段时提供：出发机场ID及归属、免费标志、已付通行费事实或`null`、当前远航开支状态。目的机场归属继续读取公开机场状态；各航班原价、实付、优惠项目和版本直接使用现有`self.quotes.flight`，不另写优惠算法。

缺少新增事实的在途旧状态显示“本次已付通行费资料未提供”，不从当前机场数量计算历史金额。现代旧局的远航收费由`travelExpense.enabled/currentAmount/preview`决定；v1明确不启用。`renderFlightCosts(state)`生成只读费用区，原飞行按钮和`flight`动作入口不变，选“不飞”也仍按原流程结束回合。

### D5：规则资料与主题接口

`buildRules()`继续作为现有规则入口，内部按主题创建导航与可展开段落。静态主题用固定ID，动态玩家名称用`textContent`或现有安全转义后显示；不把玩家输入用作HTML或导航标识。

`rulesContext(state)`统一大厅发布配置与当前局版本判断，输出机遇/股票规则版本及远航费用是否适用。机遇条目使用现有`opportunityCatalog`（大厅使用同版本本地资料），完整保留H1–H12的描述并补充限额、触发及叠加说明；不新增或改动目录中的机遇效果。

主题至少分为回合与起点、地产经营、银行与交易、机场飞行、股票、资讯与机遇、自救与联机、常见疑问。提供`rules-topic-*`固定锚点或对应展开入口；支持原关闭与焦点返回，查询规则不暂停当前决定。手机横屏提示为普通说明节点，由CSS控制展示，不绑定开始动作。

### D6：接口兼容约束

- 服务端扩展只有机场费用事实及本人只读费用投影，不新增事件、不改变动作签名或交易规则。
- 新增字段缺失不使旧状态渲染报错；v1保持原交易分支，v2旧局不因此启用远航费用。
- 股票累计限额及现金从服务端读取；本地草稿/错误/代次不写回服务端。
- 布局与规则查看不改变决定身份、截止时刻、动画顺序或世界/机遇推进。

## 模块交互（M1–M7）

### M1：状态接收、动画与手机旋转

1. 接收`gameState`后按原逻辑拒绝同局旧版本，确认本人身份，保存`latestState`。
2. 在进入动画队列之前调用`syncStockContext(latestState)`；窗口关闭、替换、身份变化时，使旧草稿、错误及回调失效。若属于旧窗口的本地请求锁仍占用，只解除该请求自己的锁，不能解除后续请求锁。
3. 继续原骰子、移动动画及机会卡票据顺序；动画未完成或`game`与最新决定不一致时，股票提交保持不可用，不用旧界面数据发动作。
4. `finishRender`按原顺序更新地图、棋子、资产、侧栏、操作栏、资讯及待处理弹窗，并根据有效股票上下文刷新预览。匹配的成功回执若正在等待最新状态渲染，在这一步再次检查。
5. 旋转和尺寸变化仅触发现有布局、棋子定位与操作栏留白计算；CSS显示或收起方向提示，不调用状态接收、动作提交或计时器初始化。短屏通过纵向滚动查看完整地图。

### M2：普通买卖与结束窗口

1. 服务端通过实际起点结算打开股票窗口，广播本人的新窗口身份及初始额度；客户端建立空上下文并自动显示股票市场。
2. 玩家调整数量，`stockPreview`核对服务端累计与草稿占用，更新可买原因、买卖金额及净现金。卖出其他城市的收入可供本批买入；最终校验仍由服务端完成。
3. 玩家点击确认，捕获当前窗口及完整订单依据；确认上下文有效、真实状态已呈现且无未确认请求，再通过原`action`事件提交。
4. 服务端按原身份、时限、报价和经营校验执行，复制状态后统一提交，先广播实际状态，再返回成功回执。客户端兼容状态或回执呈现延迟，不依赖二者紧邻到达。
5. 匹配成功回执且最新状态达到回执版本后，清理该批草稿；只有窗口仍有效、当前仍为本人股票阶段且动画完成，才按原流程发送一次`stock_done`。窗口已被超时关闭或替换时，不补发。
6. 成交后的`stock_done`若明确失败，不重新发送买卖订单；界面说明“交易已成交，窗口尚未结束”，仅允许按当前决定重试结束窗口。玩家主动放弃也绑定同一上下文，成功后的收起和清理不影响后续窗口。

### M3：失败、报价变化及连接未确认

| 分支 | 顺序与界面结果 |
|---|---|
| 提交前发现报价变化 | 保留数量，显示旧/新依据和最新金额，先提供“更新报价”；更新后重新计算限制，玩家再次点击“确认交易”才提交。更新本身不发送动作。 |
| 服务端明确拒绝 | 仅给匹配窗口显示原因；保留数量供修正。现金、持股或额度改变时显示真实限制；需要更新报价时走上一分支，不自动换价成交。 |
| 首次超时 | 仅在原窗口仍有效、连接可用且现代协议具备幂等身份时，沿用原完整载荷和`actionId`按既有次数重试；已失效窗口不重发。 |
| 重试后仍无确认 | 标记“未确认”，保留不可变原请求，不自动生成新动作身份或结束窗口；禁止把同一数量当作新订单再次提交。恢复连接及真实状态后核对，必要时显式重试原请求以获取原结果。 |
| 状态显示窗口已结束 | 按实际状态进入后续流程，失效原上下文，不以回执缺失重开股票窗口或补单；已经发生的持股、现金变化以服务端为准。 |
| 成功回执先于可用状态 | 保存该上下文的待同步成功回执，等待状态版本和渲染检查；不能用旧`actorRevision`直接发后续动作。 |
| 旧回执迟到 | 忽略其草稿、错误、弹窗及动作副作用；其请求令牌不能释放新请求的锁。不会关闭新窗口、重写新数量或误发`stock_done`。 |

对于缺少现代幂等协议的v1订单，连接未确认后不自动补发；先核对实际状态，保留原版本的交易限制。普通Socket错误通知不作为交易成功或失败结算依据，不改变股票数量、报价或窗口身份。

### M4：转让、返回与断线重连

1. 本人从股票窗口打开转让界面，仅改变展示入口，草稿上下文和服务端累计买入保留。
2. 提交转让时绑定原股票上下文；服务端进入`trade_confirm`，仍保留同一股票窗口。客户端保留上下文并暂停普通买卖提交，由接收方按原流程确认或拒绝。
3. 转让确认结束后回到原股票阶段，从真实持股重新计算预览和限制；累计买入不归零。若原草稿因转让导致持股或额度条件变化，明确标记并允许修正。
4. 本人返回市场或重连，复用服务端同一窗口身份及累计值。本地未刷新页面时保留同窗口草稿；页面重新加载时从空草稿恢复，不伪造“已买额度清零”。
5. 对局出局、解散、窗口结束或新对局时，清理对应上下文及转让草稿。迟到转让回执不得关闭新的操作弹窗。

### M5：机场结算与飞行费用说明

1. 骰子到达机场后，沿用现有奖励、归属与通行费判断。自家机场记录已付0；他人机场在原扣款完成后记录实际通行费事实；原现金不足分支继续自救，不额外创建航班或改变救援流程。
2. 进入原飞行阶段时，本人视图投影出发机场、免费标志和通行费事实，附现有各目的地报价及远航开支状态。缺少事实的旧在途状态提供未知标记，不猜测历史扣款。
3. 客户端分列“已经支付的通行费”“待确认的机票”和“结束本回合适用的远航开支”，显示出发/目的机场归属及现有优惠依据。新旧费用版本按服务端状态判断。
4. 玩家选择原飞行按钮或“不飞”，仍发送原`flight`动作。服务端按原报价校验与扣款，不因目的地属于本人改变免费条件，也不再次收目的地通行费。
5. 回合结束仍走原远航开支及必要自救流程；客户端通过实际状态/记录核对费用，不能把预告或展示金额再执行一次收费。

### M6：规则查询与焦点返回

1. 点击大厅、房间、对局或现有机遇弹窗的规则入口，通过`rulesContext`确定本次真实规则版本；大厅采用当前发布配置，已开局采用该局状态。
2. `buildRules`生成固定主题导航、规则段落、十二项机遇及五类常见疑问示例；动态名称安全插入。
3. 主题跳转或展开只改变本弹窗阅读状态；滚动和布局允许手机、平板及PC阅读完整说明，不暂停当前决定、不发送动作。
4. 关闭规则回到原界面并恢复入口焦点；若查询期间服务端决定已变化，显示最新有效操作，不重新打开过期决定。倒计时与其他强制弹窗仍按原状态处理顺序显示。

### M7：资源更新与有限验证

1. 同批更新HTML中的CSS/JS版本及Service Worker缓存名和资源清单，沿用现有导航网络优先与静态资源版本缓存方式。

3. 使用现有测试工具按AC1–AC19准备有限场景，分别记录手机隐藏文字修复、股票异常复现/防护与正常交易、费用一致性及规则查找结果。
4. 只把实际验证通过的任务和条目标为完成；失败则修复并重跑相关场景，不追加完整长局或胜率模拟。具体命令、次数和范围在task.md及checklist.md固定。
